# 桌面端设备授权和独立网页发布

核对日期：2026-10-15。对应本仓库服务端和 `E:/shroom1` 的 `agent` 分支；部署及实测状态见各节，源码能力不等于客户软件已更新。

## 部署顺序

1. 备份数据库，部署服务端代码并执行 `pnpm db:migrate`。本次增加 `0020_license_device_limits.sql`：`license_device_policies` 和 `license_devices`，分别按密钥类型/ID、密钥类型/ID/电脑摘要建立唯一约束。
2. 保留现有 `SHROOM_SYSTEM_PACKAGE_SIGNING_KEY_PATH`，必须是与桌面端内置公钥配对的 Ed25519 私钥；不要重新生成不匹配的密钥。
3. 配置 `SHROOM_FRONTEND_RELEASE_DIR=/data/html` 为独立、持久的前端发布目录。现有部署工作流创建服务器绝对路径 `/data/html`，写入 `.env` 并通过 PM2 更新环境，目录在仓库外，后续部署不会删除历史版本。
4. 发布一次包含设备授权、网页缓存及统计 IPC 的新版 Shroom 安装包。只有前端源码更新不能改变旧软件的主进程能力。
5. 用测试客户验证同机升级不重复登记、超额拒绝、解绑与恢复、暂时断网；最后发布兼容网页并确认完整缓存、下次启动及失败回退。

本轮没有执行生产迁移、读取生产私钥、发布前端版本或替换客户安装包。

## 管理网站 CI 部署（2026-10-19）

管理网站的 Deploy 工作流在 GitHub runner 上执行检查、测试和构建，并由 `scripts/build-deploy.mjs` 将 Node 运行依赖、迁移执行器、注册表和 SQL 一起打入自包含 `dist`，再通过 SCP 传送带 SHA-256 的构建包。生产机不再执行 Git fetch/reset、依赖安装或构建，也不需要读取原有 node_modules。部署前要求 Node.js 22+、至少 2 GiB 可用磁盘、256 MiB 可用内存和 50000 个空闲 inode；资源不足就停止，现有运行版本不切换。

服务器已有 `.env` 会原样保留，只有首次缺少文件时才从 GitHub Secrets 创建；以后修改飞书、数据库或 JWT 配置应更新服务器文件并重启 PM2。签名私钥继续使用原来的配对文件，不上传本地 `.env`。

服务器通过 `deploy-server.sh` 串行发布；解包、校验、迁移和清理以 nice 10 及可用时 ionice best-effort 7 执行，不承诺云盘 IOPS 硬上限。迁移复用标记绑定 SQL 历史和数据库连接目标，未变化则不连接数据库，变化时仍由原 Drizzle MySQL 迁移语义执行，超时120秒，成功才写标记。重启后连续3次检查 `/healthz` 的实际运行提交与首页内容，失败恢复整个上一版dist；数据库迁移不自动回退，生产迁移前仍需按原流程备份。

`/opt/key-manager-deployments` 仅保存有限的部署记录：最近2份成功、1份失败和当前任务；超过24小时的有标记prepared任务可清理。CI上传时就附带管理标记，以便后续收回SSH尚未执行时留下的完整上传。成功后删除压缩包及解包临时文件，保留上一版构建用于回退；只在退出时清理一次。脚本忽略未标记、非数字run-attempt目录和符号链接；不清理数据库、日志、原node_modules、`/data/html`或私钥。日志轮转属于单独的运维配置。排查当前版本应读取 `dist/release.json`，服务器Git HEAD不再代表正在运行的版本。详见 `docs/low-io-deployment.md`；此方案本轮仅本地验证，尚未发布到生产。

## 管理电脑数量

### 普通密钥与限制密钥分类（2026-10-15）

- 原有“生成密钥 / 密钥管理”和“生成离线密钥 / 离线密钥管理”入口只生成或展示不限电脑数量的普通密钥。
- 侧栏新增“限制密钥”分类，包含“生成限制密钥”（`/limited-generate`）和“限制密钥管理”（`/limited-keys`），每页可切换在线、离线模式；`?type=offline` 可直接进入离线页签。仅 `super_admin` 可使用这两个入口，普通密钥沿用原权限。
- 限制密钥生成必须填写 1–10000 台电脑，默认 1 台；在线单个、在线批量、离线签发均支持。批量中的每把密钥分别拥有指定数量。在线密钥记录和初始电脑策略在同一事务内保存，离线限制码也是如此，策略保存失败不会遗留可用的无限制码。
- 在线/离线列表、在线 CSV/JSON 导出、离线统计按 `deviceMode: "unlimited" | "limited"` 在数据库过滤后再分页。接口省略该字段或传 `all` 时沿用旧调用的全部记录范围；客户和创建人可见范围保持不变。列表返回当前 `deviceLimit` 和 `deviceRestricted`。
- 已有在线密钥根据当前策略自动归类；从“电脑授权”改为正上限后进入限制分类，设为 0 后回到普通分类。v4 离线限制码即使当前策略改为 0，仍留在限制分类并显示“不限量（新版授权）”，因为其签名格式仍要求新版客户端。
- 普通在线 AES 密文结构不变，普通离线 RSA 码不添加限制字段；旧客户端是否支持具体授权范围仍取决于其版本和内置公钥，不能仅凭“不限量”保证全部旧版本兼容。限制密钥明确提示需要新版客户端。在线受限密钥重签继承当前电脑上限，且只有 `super_admin` 可重签受限密钥。

`super_admin` 在在线/离线密钥列表的“电脑授权”按钮中设置上限、查看电脑摘要后 8 位和最近验证时间，并解绑/恢复。0 默认不限量，设置范围 0–10000。降低到低于已登记数量时先解绑，恢复也遵守上限；操作沿用审计日志。

`POST /licenseCheck` 增加 `deviceId` 入参，数据库有效的密钥按策略登记并返回 `deviceLimit` 与 `deviceLease: { lease, signature }`。有效的现代客户端得到最长 7 天、绑定电脑和密钥摘要、且不超过密钥有效期的签名凭证。无电脑 ID 的旧调用只有在不限量时兼容；有限数量时返回 `DEVICE_ID_REQUIRED` 和过期结果，避免旧远程验证缓存误判。更老的纯本地验证客户端必须升级，服务端无法追溯强制限制它们。

策略行在事务中先 `SELECT … FOR UPDATE`，计数、登记、解绑和恢复使用同一策略锁，避免同一名额被并发领走。已解绑电脑不能自动重新登记；同一电脑重复验证更新最后验证时间，不占新名额。数据库或签名配置不可用时返回服务不可用，不降级取消限制。

签名凭证最长离线 7 天，因此解绑无法即时触达断网电脑。即使当前策略不限量，新版在线客户端也保留有期限的凭证，以便后续改变数量策略或吊销。

### 人工审核补录旧在线密钥（2026-10-15）

历史 AES 密钥可能能解密但不在当前授权库。现代 `/licenseCheck` 请求携带 `deviceId` 时，对此返回 `valid: false / LICENSE_NOT_REGISTERED`，提示管理员补录原密钥；数据库不可用返回 503。无 `deviceId` 的旧调用保留原 `UNKNOWN` 兼容行为。不能在公开接口上把任意可解密字符串自动登记为授权。

管理员核对原密钥来源、系统范围及到期时间后，在服务器项目根目录执行以下命令；密钥通过受控 STDIN 输入，不放进命令参数、聊天日志或版本库。第一遍默认只预览，不修改数据库：

```powershell
$reviewedKey | pnpm exec tsx scripts/register-legacy-license.ts --operator-id <活跃超级管理员ID> --reason "人工审核的具体依据"
$reviewedKey | pnpm exec tsx scripts/register-legacy-license.ts --apply --operator-id <活跃超级管理员ID> --reason "人工审核的具体依据"
```

命令保留原密钥字符串、动态分类令牌和精确到期时间，默认电脑数量不限量；登记与脱敏审计在同一事务中完成。已有正常记录返回 `EXISTS`，不覆盖原配置；已有暂停、吊销、过期或软删除记录拒绝补录，不能通过此命令恢复。仅活跃 `super_admin` 可作为审核操作人，命令不能替代签发来源的人工核对。

补录后用实际客户电脑请求 `/licenseCheck` 并验证签名、密钥/电脑绑定、原有效期及离线凭证；不要仅以“能解密”或返回 `valid: true` 视为验收。本轮对一把用户反馈的旧密钥完成了生产补录及当前客户端验签、签名缓存验证；此处通用路由及工具源码尚未部署到常驻服务，不需要数据库迁移。

### 离线密钥

默认仍生成原来的不限量 RSA 离线码。在“限制密钥 → 生成限制密钥 → 离线密钥”设置电脑数量后签发 v4，签入 `deviceLimit` 和 `boundSensorTypes`，新版客户端通过 `POST /api/license/devices/check` 验证服务器登记记录、RSA 签名、状态与到期时间，然后登记电脑并取得短期签名凭证。

v4 故意使用新授权范围字段：不支持设备授权的旧客户端不能把它当作无限制离线码接受。公司系统包授权解析也支持 v4 的签名范围。旧不限量离线码没有签入这一机制，不能仅改数据库追加数量限制；网站会提示重新签发。不要向客户把“有限设备的离线码”描述成永久不需要联网。

## 独立发布前端网页

先在桌面项目按现有 Vite 配置构建前端，完成业务回归。将构建目录传至发布服务器，在 `E:/key` 对应部署仓库运行：

```bash
export SHROOM_FRONTEND_RELEASE_DIR=/data/html
export SHROOM_SYSTEM_PACKAGE_SIGNING_KEY_PATH=/opt/key-manager-secrets/system-package-private.pem
pnpm exec tsx scripts/publish-frontend-release.ts /path/to/shroom/build 1.1.37
```

第二个参数必须填写实际支持这些功能的最低安装包版本。上面的版本只演示格式；仓库仍为 1.1.37，发布新安装包时应按正式发版流程增加版本号，并使用那个版本。可传第三个正整数参数指定 `releaseId`，否则使用当前毫秒时间；脚本强制新 ID 大于已发布最新 ID。原代码回退也应以更大的发布 ID 重新发布。

Shroom 的 Vite 新配置自动生成 `frontend-build.json`，包含真实构建毫秒编号与安装包版本；发布脚本必须读取这个文件，把 `buildId` 签入清单。旧构建目录缺少该文件时需重新构建，不应手工补编号。构建机保持正确时间；发布顺序和代码构建顺序分别由 `releaseId`、`buildId` 表达，旧代码晚发布仍不能覆盖比它新建的安装包页面。

网页构建资源可先上传到 `/opt/shroom-web-upload/build/`，再将这个目录作为脚本的第一个参数。正式发布目录由脚本生成：

```text
/data/html/
├── latest.json
└── 版本ID/
    ├── release.json
    ├── frontend-build.json
    ├── index.html
    └── assets/
```

`latest.json` 与 `release.json` 由服务器发布脚本签名生成，只有完整发布完成才更新最新版本入口。`/data/html` 是服务器磁盘路径，HTTP 下载继续由已定义的前端更新接口提供。此路径变更尚未部署，旧正式目录如已有版本也需在部署时核对迁移。

脚本先枚举、校验、签名，在隔离的 `.publish-*` 目录组装完整资源，再原子替换 `latest.json`。与上次发布相同哈希/大小的资源先复验字节，使用硬链接共享磁盘块；不支持时复制，损坏时重新从上传构建复制。只在已发布版本之间共享，绝不链接以后可能被覆盖的上传输入。发布 ID 不可覆盖，失败不改动现有 latest；已重命名但未切换 latest 的孤立目录以后清理。`model/`、`models/`、`uv/`、`.map`、隐藏文件和 `config.txt` 排除，继续由兼容安装包提供。只接受安全路径、含 index.html 与 JS 的构建，限制 2000 文件、64 MiB/文件、256 MiB/版本。发布目录不能与输入构建目录重叠。

每次发布成功后自动清理旧目录：保护 latest、最近 5 个版本及目录生成后 24 小时内的版本。宽限期避免中断正在下载的客户端，因此可能暂时多于 5 个版本；长期不会按全部历史持续保留。不相关目录不删除，正式目录不存放聊天/数据库。旧版本完全缓存到客户本机后，服务器删除其目录不影响离线运行。脚本结果输出复用字节数与删除版本数。

`.publish.lock` 用排他创建防止同时发布导致 latest 倒退，正常成功/失败均释放；进程被强制终止后，需要先确认没有发布进程，再删除遗留锁及 `.publish-*` 临时目录。不要在发布进行中清理锁。输入上传目录独立于正式库，其保留/清理仍由运维管理。

| 路由 | 行为 |
| --- | --- |
| `GET /api/frontend/latest` | 返回签名清单，服务端复验签名；`no-store`；未配置时 503 JSON |
| `GET /api/frontend/releases/:id/*` | 仅提供该版本清单登记的资源，保持正确 MIME；不可变缓存；不存在时 404 JSON |

客户端以安装包内公钥验证签名和每个文件的 SHA-256，只加载构建编号比安装包网页更新的兼容缓存。按哈希复用本地字节，只下载发生变化的文件，但启用前仍形成完整资源目录；保留当前、上一成功、待启用及正在运行版本，自动清理多余历史。无网继续使用本地页面，新版后台缓存后下次启动启用，运行中不替换 JS/CSS，启动确认失败回退。需要新增 IPC、原生依赖、Python 能力或模型资源的版本必须先更新安装包。前端清单的 `hostContract: 1` 只支持当前宿主契约。

## 使用统计和错误上报

服务端沿用现有 `/api/usage/events/batch`、`usage_*` 表、`/usage-analytics` 超管统计页面。本轮主要新增桌面采集端，无新增统计表。首次使用默认开启，客户在软件“应用设置”可查看上传范围并关闭，升级保留已保存的开关选择；与 Agent 聊天同步独立。

首批埋点：会话、系统进入与停留、串口连接、采集开始/结束与时长、回放启动、CSV 导出、Agent 任务结果，以及公共后端日志、页面和 Electron 异常。上传有限属性和脱敏错误，不包括聊天、原始帧、附件或自定义系统名称；切换密钥隔离队列，以确实送达的事件 ID 做幂等回执。

统计鉴权同时接受已登记的在线软件密钥和有效离线 RSA 激活码；复用聊天上传的实际签名/状态/客户核验，来源分别关联在线或离线登记记录。未登记、撤销、过期或关联客户无效时拒绝，客户身份不可由客户端指定。须已执行 `0021_agent_chat_offline_sources.sql`；本轮没有新增迁移，超管读取权限与历史归属保持。

新版 Shroom 补齐调节/工具、算法状态、Agent 方案、连接首帧和断流、授权、更新、采集回放及系统操作，继续批次发送版本 1 白名单事件。管理页已增加中文功能/动作和帧、已提交行、MiB 单位；接收速率不等于丢帧率，安装器交接不等于安装成功。不接收调节值、采集标签、原始压力或算法源码；与聊天正文同步开关独立。详细频率和结果定义见配套 `E:/shroom1/docs/desktop-distribution-services.md`。
